WizPulseAI 矩阵网站账号、Cookie、付费与产品扩展架构说明

这份资料用“人能读懂”的方式总结当前矩阵网站的账号体系、子域登录共享、积分/Stripe 设计、各 App 扩展方式，以及我在代码 review 中发现的具体问题和建议路线。

生成日期：2026-05-14 范围：只读 review，无业务代码修改 重点：注册、SSO、Cookie、付费、ExpoGeo 接入

1. 一句话总览

当前矩阵网站的方向是正确的：把登录注册放在 auth，把付费、用户中心、积分、权益放在 dashboard/db，每个产品 App 保持独立。这样未来可以继续增加 ExpoGeo、Dino、Fashion 等产品，而不需要每个 App 都重复做账号和付费。

现在的问题不是“大方向错了”，而是底座代码里有一些半成品和历史遗留：订阅字段不一致、redirect 校验不够安全、Stripe checkout 校验不完整、积分充值并发不够稳、SSO cookie 的安全边界需要统一说明。它们在早期可以跑起来，但不适合直接作为长期商业系统的底座。

2. 当前矩阵网站由哪些部分组成

主站

wizPulseAI-com

负责品牌、内容、入口、SEO、产品介绍。它不应该承载复杂付费逻辑。

认证中心

auth-wizpulseai-com

负责登录、注册、OAuth callback、logout、语言 cookie 同步、跨子域登录跳转。

用户/付费中心

db-wizPulseAI-com

负责 dashboard、用户资料、订阅、积分、Stripe webhook、管理员后台、权益判断。

产品站：Fashion

fashion-wizpulseai-com

独立产品 App，使用矩阵账号和积分，不自己处理 Stripe 底层。

产品站：ExpoGeo

ExpoGeo

国家学习工具，后续应接入矩阵账号、权益、学习进度同步，但保留独立代码仓库。

其他产品站

dino-kids-app 等

适合按同样模式扩展：独立产品体验，共用账号和付费底座。

3. 注册和登录应该如何工作

用户在产品站点击登录 例如 ExpoGeo 的“登录/保存进度”按钮。
跳到 Auth 中心 URL 带上 redirect_to，说明登录后回到哪里。
Supabase 完成认证 邮箱、OAuth、magic link 等流程都应收口在 auth。
带 session 回到产品站 产品站读取共享 cookie，得到登录状态。
正确的产品站接入方式不是“每个 App 自己做一套注册登录”，而是每个 App 都把用户送到统一的 auth 中心，登录完成后再回到原 App。

当前需要修正的点

问题 影响 建议
redirect 白名单用 startsWith 判断 可能被伪造域名绕过，形成开放重定向风险。 改成解析 URL 后比较 origin，使用环境变量管理允许域名。
callback 中相对路径会回到 auth 自己 如果某些入口传的是 /xxx，登录后不一定回到原产品站。 产品站传绝对 URL，auth 只允许白名单 origin。
多个 auth helper 实现并存 不同站点的 cookie 行为可能慢慢分叉。 抽成共享包或固定复制源，减少重复实现。

4. 子域 Cookie 和 SSO 的本质

现在的目标是让 www.wizpulseai.com、auth.wizpulseai.com、dashboard.wizpulseai.com、geo.wizpulseai.com 这些子域共享登录状态。核心方式是把 Supabase session cookie 写到顶级域 .wizpulseai.com。

.wizpulseai.com 顶级 cookie 子域都能读取同一份登录状态，因此用户登录一次，可以在多个产品间切换。
适用于
auth写入/刷新登录 cookie。
dashboard读取登录状态，展示账户和付费。
Fashion读取登录状态，调用积分/权益。
ExpoGeo未来读取登录状态，保存学习进度。
需要注意：当前 browser client 使用 document.cookie 写 Supabase auth cookie，这类 cookie 无法设置为 HttpOnly。如果文档里承诺的是完全服务端 HttpOnly 模型，就需要统一实现或调整文档表述。

我建议的安全边界

  • 登录 token 只服务于身份识别，不把高风险管理动作放在纯前端判断里。
  • 所有付费、扣积分、发权益，都必须由 dashboard/db 后端二次校验。
  • 产品站可以读“我是谁”和“我有什么权益”，但不能自己决定付款是否成功。
  • 跨域跳转必须走 allowlist，新增产品域名必须显式加入。
  • 后续如果商业化增强，应优先考虑更严格的服务端 session/cookie 策略。

5. Stripe、积分和订阅的设计

你现在实际使用的是 point 买断模式，每个 App 可以有自己的积分消费场景。订阅代码目前还没有真正上线，属于半成品状态。我的建议是：短期把积分买断做稳，中期再把订阅补完整。

推荐的付费分层

类型 适合用途 应该由谁管理
积分买断 图片生成、单次 AI 调用、某个 App 的消耗型功能。 Dashboard 统一收款和记账，产品站调用积分 API。
订阅 持续权益，例如高级地图、完整音频、专题内容、家庭账号。 Dashboard 管 Stripe subscription，产品站只读权益。
单 App 买断包 例如 ExpoGeo 某个国家包、文化包、离线语音包。 可以仍然通过 Dashboard checkout，记录到产品权益表。

当前付费代码的具体问题

优先级 问题 为什么重要 建议动作
P1 订阅表字段使用不一致：stripe_id 与 stripe_subscription_id 混用。 取消、恢复、webhook 同步可能失效。 统一成数据库实际字段，补测试。
P1 Stripe price id 查本地价格时可能查错字段。 Stripe 返回的是 price id，通常应匹配本地 prices.stripe_id。 确认数据模型后统一查询逻辑。
P2 订阅 checkout 接收客户端传来的 priceId。 用户可能传入不应该购买的 Stripe price。 服务端先查本地 active/public price，再创建 checkout。
P2 积分充值先读余额再写余额，不是原子操作。 并发购买时理论上可能丢积分。 用数据库 RPC 做 add_credits，类似扣积分。
P2 success/cancel URL 可由客户端传入。 可能出现跳转到非预期页面的问题。 限制到允许域名，或按 product 在服务端生成。

6. 不同 App 应该如何快速扩展

新 App 不应该复制一整套登录、用户表、Stripe、积分系统。它应该只实现自己的产品体验，然后通过矩阵底座拿到身份、权益和消费能力。

产品 App 自己负责

  • 核心用户体验和页面。
  • 本地状态和游客体验。
  • 调用产品自己的业务 API。
  • 展示登录、订阅、积分余额入口。
  • 根据权益开关隐藏或开放功能。

矩阵底座统一负责

  • 注册、登录、OAuth、logout。
  • 跨子域 SSO cookie。
  • Stripe checkout、webhook、退款/取消。
  • 积分余额、交易记录、权益判断。
  • 管理员后台和用户中心。

标准接入清单

  1. 给产品确定域名，例如 geo.wizpulseai.com。
  2. 把产品域名加入 auth redirect allowlist 和 Supabase redirect settings。
  3. 产品站接入共享 auth helper，读取当前用户。
  4. dashboard 创建 product code，例如 expo_geo。
  5. 定义 feature code，例如 expo_geo.audio、expo_geo.real_map。
  6. 产品站调用权益接口，决定功能是否开放。
  7. 需要跨设备同步时，再把 localStorage 里的游客数据迁移到数据库。

7. ExpoGeo 的融合路线

ExpoGeo 现在最适合先作为免费学习工具推出，再逐步接入账号、进度同步和付费权益。不要一开始就把它变成复杂的付费系统。

阶段 目标 具体内容
Phase 0 独立稳定运行 ExpoGeo 保持独立目录和仓库，完成国家学习、搜索、地图、基础多语言 UI。
Phase 1 接入矩阵登录 增加登录按钮、用户状态、跳转 auth 后返回 ExpoGeo。
Phase 2 接入权益 dashboard 增加 expo_geo 产品和功能码，ExpoGeo 读取权益。
Phase 3 同步学习记录 游客继续用 localStorage；登录后同步收藏、已学国家、测验记录。
Phase 4 商业化内容 高级语音、国家专题、真实地图入口、旅游/商务会话包、儿童模式。
对 ExpoGeo 来说，短期不需要单独数据库。游客数据用 localStorage 足够。只有登录用户的跨设备同步、付费权益、收藏和学习进度，才需要接入矩阵数据库。

9. 推荐的下一步

  1. 先修 auth redirect，让新增产品域名接入时不会留下安全问题。
  2. 整理付费模型：短期以 point 买断为主，订阅代码先修到“不坏”，但不急着开放。
  3. 把积分充值改成数据库原子操作，这是当前真实业务更需要的稳定性。
  4. 为 ExpoGeo 做最小登录接入：登录状态、登录按钮、用户菜单、跳转 dashboard。
  5. 再做统一权益接口，让所有产品 App 都用同一套判断方式。
核心原则：产品 App 要快，底座要稳。ExpoGeo 这类 App 应该专注学习体验，不要背负账号、Stripe、权限、账单这些复杂逻辑。
