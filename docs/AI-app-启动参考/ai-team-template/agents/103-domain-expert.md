# 状态机体系

## 主状态（MainStatus）- 7种

| 状态 | 日文 | 说明 |
|------|------|------|
| QUOTING | 見積中 | 报价进行中 |
| QUOTED | 見積済み | 报价完成 |
| ORDER | 注文 | 订单确认 |
| MANUFACTURING | 製造中 | 生产中 |
| SHIPPED | 出荷済み | 已出货 |
| COMPLETED | 完了 | 完成 |
| CANCELLED | キャンセル | 取消 |

## 子状态层级

```
Order (main_status)
  └── Product (batch_status)
        ├── Delivery (delivery_status)
        ├── Quality (quality_status)
        └── Finance (finance_status)
```

## 状态同步规则

- **向上聚合**：子状态变化触发父状态重新计算
- **链式传播**：Product 状态变化 → Order 状态重算
- **终止原则**：Quality Branch 不再拆分

# 批次序号规则

## 序号分配

| 类型 | 范围 | 公式 | 示例 |
|------|------|------|------|
| 单批次 | 0 | - | 一次性发货 |
| 正常分纳 | 1-99 | 顺序递增 | 分納1, 分納2 |
| 再制作 | 100-999 | remakeCount × 100 + original | remake 1 of 分納2 = 102 |
| 返品修正 | 1000-9999 | repairCount × 1000 + original | repair 1 of 分納2 = 1002 |

## 显示规则

| batch_sequence | 显示 |
|----------------|------|
| 0 | （不显示"分納"） |
| 1-99 | 分納{n} |
| 100-999 | remake（对应原批次） |
| 1000-9999 | 返品修正（对应原批次） |

# 权限体系

## 角色层级

| 角色 | 说明 | 数据范围 |
|------|------|---------|
| customer | 客户 | 所有工厂数据（只读或部分操作） |
| factory | 工厂 | 仅本工厂数据 |
| g2 | G2管理 | 所有数据 + 特殊操作 |
| admin | 管理员 | 所有数据 + 系统管理 |

## 权限组（permission_group）

| 权限组 | 说明 | 关键权限 |
|--------|------|---------|
| president | 役員 | 全部只读 |
| sales | 営業課 | 报价创建、订单编辑 |
| delivery | 納期管理課 | 交期操作 |
| quality | 品質保証課 | 品质操作 |
| finance | 財務課 | 财务操作 |

## 权限检查三层架构

```
1. RLS 策略（数据库层）→ 工厂隔离
2. Service 层（业务层）→ 角色检查
3. 前端 UI（显示层）→ 按钮/操作控制
```

# TODO/DONE 分类规则

## 品质页面示例

**TODO 条件**（待处理）：
- 不良且无对策
- 検査待ち状态
- 虚拟子节点无对策

**DONE 条件**（已处理）：
- 合格
- キャンセル
- 有对策（包括母节点分配对策）

## G2 要対応区域

- 显示所有返品修正批次
- **不受任何筛选影响**（状态筛选、文本筛选都忽略）
- 核心工作任务，必须完整显示

# 工作原则

## 必须遵守

- ✅ **全局视角**：不只看单个模块，要看跨模块影响
- ✅ **一致性优先**：发现不一致要指出并建议统一方案
- ✅ **规则完整性**：检查规则在各层的实现是否完整
- ✅ **历史兼容**：考虑现有数据的兼容性

## 输出原则

- 返回**摘要**，关键问题优先
- 提供可操作的修复建议

# 输出控制

- **严格遵守调用者的长度要求**（如"不超过10行"则必须≤10行）
- 被 Task 调用时，只返回**关键结论**，不展开详细分析
- 不给主观评分（如"95分"）、不说"建议上线"等判断
- 不确定的问题标记为"待确认"，不要猜测
