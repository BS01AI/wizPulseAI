## 4. API调用链与成本明细

> 每一次用户操作，后台发生了什么，花了多少钱

### 4.1 用户操作 → API调用 → 真实成本 一览表

| 用户操作 | 外部API调用数 | 数据库操作数 | AI成本 | 积分消耗 | 真实成本 |
|---------|-------------|------------|--------|---------|---------|
| 上传照片 | 2 (Auth+Storage) | 3 | ¥0 | 0pt | ¥0 |
| **分析照片(Standard)** | **3 (Auth+Storage+Gemini)** | **8** | **¥0.16** | **9pt** | **¥0.16** |
| **分析照片(Premium)** | **3** | **8** | **¥0.16** | **23pt** | **¥0.16** |
| 查看历史 | 1 (Auth) | 2 | ¥0 | 0pt | ¥0 |
| 查看余额 | 1 (Auth) | 1 | ¥0 | 0pt | ¥0 |
| 购买积分 | 3 (Auth×2+Stripe) | 0 | ¥0 | 0pt | Stripe 3.6% |
| Webhook(积分到账) | 1 (Stripe验证) | 3 | ¥0 | 0pt | ¥0 |

> **关键发现**: Standard和Premium模式调用**同一个AI模型**（gemini-3-flash-preview），真实成本一样。Premium只是收更多积分。

### 4.2 AI分析 - 完整调用链（最核心、最贵的操作）

```
用户点击「分析する」
  │
  ├─ 1. 认证检查 → Supabase Auth API
  ├─ 2. 频率限制检查 → Supabase RPC: check_rate_limit
  ├─ 3. 用户偏好查询 → Supabase RPC: get_user_personalization
  ├─ 4. 照片数据查询 → SELECT fashion.user_photos
  ├─ 5. 照片状态更新 → UPDATE → "analyzing"
  ├─ 6. 生成签名URL → Supabase Storage (1小时有效)
  │
  ├─ 7. ⭐ AI调用 → Google Gemini Vision API
  │     模型: gemini-3-flash-preview
  │     输入: 1024px WebP图片 + 系统Prompt
  │     输出: JSON格式分析结果
  │     Token: ~1,058(输入) + ~1,500(输出) = ~2,558
  │     耗时: ~3-10秒
  │     💰 成本: $0.001 ≈ ¥0.16
  │
  ├─ 8. 积分扣除 → UPDATE user_credits + INSERT credit_transactions
  ├─ 9. 保存分析结果 → INSERT fashion.analyses
  └─ 10. 更新照片状态 → UPDATE → "completed"
```

## 5. 流量控制与限额设计

> 防止滥用、控制成本、保证服务质量

### 5.1 用户级限流（当前已实施）

| 功能 | 每小时 | 每天 | 每周 | 每月 |
|------|--------|------|------|------|
| 照片分析 | 10 | 50 | 200 | 400 |
| 穿搭生成 | 3 | 10 | 30 | 50 |
| 分享创建 | 10 | 30 | 100 | 200 |

**限流实现**: 数据库持久化的多窗口限流器（按用户ID+功能）

### 5.2 限流的成本意义

**最坏情况**（单用户月400次分析）:
```
AI成本: 400次 × ¥0.16 = ¥64
如果用户买ライト(¥500): 实际只够 500/9 = 55次
如果用户买メガ(¥5,000): 实际只够 5400/9 = 600次

结论: 积分本身就是天然限流。用完积分就停止。
      速率限制主要防恶意调用（如脚本刷API）。
```

### 5.3 Gemini API 免费额度

| 指标 | 免费额度 | 超出后 |
|------|---------|--------|
| 每分钟请求 | 15次 | 按量付费，无硬限 |
| 每天请求 | 1,500次 | 按量付费 |

**15次/分钟的并发瓶颈**:
```
15次/分 = 同时最多服务15个用户的分析请求
如果平均分析耗时5秒，理论吞吐量 = 15 × (60/5) = 180次/分

现实场景: 除非同一分钟有15+人同时点分析，否则不会触发
预计在1000+日活用户时需要关注
```

### 9.2 数据安全

#### 用户照片处理流程

```
用户上传 → 压缩800px(AI分析用，不存储)
         → 生成200px缩略图(私有存储)
         → 生成48px微缩略图(私有存储)
         → 原图丢弃
         → AI分析完毕后压缩图也丢弃
```

#### 已实施的保护

| 措施 | 说明 |
|------|------|
| 原图不存储 | 分析完即丢弃 |
| 私有存储桶 | Supabase Storage，签名URL访问 |
| 签名URL有效期 | 1小时（3600秒） |
| 文件类型验证 | MIME type白名单 |
| 文件大小限制 | 有最大限制 |
| 上传配额 | 每用户有上传频率限制 |
| 分析限流 | 时/日/周/月 多窗口限制 |

#### 需要改进的项目

| 项目 | 优先级 | 说明 |
|------|--------|------|
| Upload API错误信息泄露 | P1 | 生产环境不应返回stack trace |
| Analyze API调试信息 | P2 | 生产环境不应返回userId等内部数据 |
| 日志PII脱敏 | P2 | 日志中含用户邮箱，需脱敏处理 |

### 9.3 环境安全

#### 需要立即处理的问题

| 问题 | 严重度 | 说明 |
|------|--------|------|
| `.mcp.json` 含测试密钥 | **高** | Stripe test key、Supabase token、Notion token 在代码中 |
| 迁移脚本含 Service Role Key | **高** | fashion站scripts/目录下硬编码了Supabase管理密钥 |
| dev-mode含真实用户ID | 中 | 虽有生产环境保护，但泄露了真实UUID |

```
1. 轮换(Rotate)所有已暴露的密钥
2. 从代码中删除硬编码密钥，改用环境变量
3. 确认 .gitignore 覆盖 .mcp.json
4. 使用 git filter-branch 或 BFG 清理历史
```
